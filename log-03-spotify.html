Controlling Spotify Reliably: From API-Free Automation to Search-First Playback

The network resolves the track. The device plays it. A read-only Spotify Web API integration identifies spoken requests, while Android intents and media-button events handle playback and Room stores listening history locally.

1. Starting without an APIThe original implementation used two Android mechanisms to control Spotify.Playback navigation through deep linksFor known tracks, LocaLL opens a Spotify URI using an ACTION_VIEW intent explicitly targeting com.spotify.music.spotify:track:For unknown tracks, it can open Spotify search:spotify:search:Playback controls through media-button eventsPause, resume, skip, and replay are sent through AudioManager.dispatchMediaKeyEvent().Android routes these events through its media-key handling system rather than sending them directly to Spotify. This avoids a Spotify SDK or API integration, but it also means delivery depends on Android's current media-key routing and active media session. Another app's media session can take priority, and background execution does not guarantee that Spotify receives every event.I treat these commands as best-effort rather than assuming that dispatching an event means playback state has changed.The approach was simple: open Spotify with the requested track and use media keys to control playback.Then I started testing it with actual voice commands.

2. Opening a track doesn't necessarily play itThe first problem was that opening a spotify:track: URI only navigated Spotify to the requested song.On the Spotify builds I tested, the track loaded into the player in a paused state. The deep link worked, but no music started.There was no reliable play parameter to add to the URI, so I separated navigation from playback.After opening the track, LocaLL sends a MEDIA_PLAY event. Since Spotify might still be cold-starting, the event is sent through spaced retries.fun playUri(uri: String): Boolean { if (!openSpotify(Uri.parse(uri))) return false scope.launch { // Spaced retries to cover a cold Spotify launch. for (waitMs in longArrayOf(1500, 1500, 2000)) { delay(waitMs) sendKey(KeyEvent.KEYCODE_MEDIA_PLAY) } } return true}The choice of key event matters.MEDIA_PLAY requests playback without toggling the current state. If Spotify has already started playing, another play request should not pause it.Using MEDIA_PLAY_PAUSE would be risky because it toggles playback. A retry could pause a track that had already started.These retries are still blind. They don't confirm that Spotify received the event or that audio actually started. They also cannot override Android's media-session routing decisions.

3. The problem with unknown songsThe local catalogue could handle known songs, but it couldn't cover everything a user might ask for.For an unknown song, opening a spotify:search: URI only displays search results. It doesn't select or play anything.My first solution was to automate Spotify's search interface using an Android Accessibility service:Open Spotify search.Enter the requested query.Select the top result.The music module received this capability through a callback rather than depending directly on the Accessibility service.This worked, but it introduced another layer of fragility. Spotify could change its layout, the top result wasn't always the right one, and LocaLL had no reliable way to confirm whether the interaction succeeded.If Accessibility access was disabled, the app could only open search and ask the user to select a result manually.This was the point where the API-free approach started becoming a limitation.

4. A small API integration to solve track resolutionInstead of trying to make UI automation more reliable, I changed the architecture.LocaLL now uses the Spotify Web API's search endpoint to resolve a spoken request to a concrete track URI.The API is used for one purpose: finding out which Spotify track matches the request.It does not start playback, pause music, skip tracks, or control the media session.The flow is:Receive the spoken request.Search Spotify using the request.Extract the matching track's URI.Pass that URI to the existing playUri() implementation.Let Android handle opening Spotify and starting playback.The API integration uses the client-credentials grant. It obtains an application access token without requiring the user to log in or grant account permissions through a user-consent screen.The resolver is also optional:val isConfigured: Boolean get() = BuildConfig.SPOTIFY_CLIENT_ID.isNotBlank() && BuildConfig.SPOTIFY_CLIENT_SECRET.isNotBlank()suspend fun resolveTrack(query: String): Track? { if (!isConfigured) return null val token = accessToken() ?: return null return search(token, query)}Credentials are kept in local.properties, which is git-ignored, and injected into BuildConfig at build time.There is an important security trade-off here. This is a personal project that I build and install directly on my own device, so bundling the client credentials into the APK is acceptable for my current use case. However, local.properties only prevents accidental source-control commits. It does not protect the secret once the APK is distributed; someone can extract it from the application.For a public app, the client secret should stay on a backend that proxies the search request. If the app needs user-authorized Spotify access, an appropriate user authorization flow such as Authorization Code with PKCE would be needed instead.If the credentials are missing or resolution fails, the resolver returns null and LocaLL falls back to its original API-free paths.The API improves track resolution without becoming a requirement for the rest of the feature.

5. Resolution order: deterministic first, best-effort lastWith the API integration, MusicCommandHandler follows a resolution order that prioritizes known information before falling back to less reliable approaches.OrderResolution pathResult1Local catalogueKnown track URI2Spotify Web API searchMatching track URI3Local LLM extracts title and artist, followed by another resolution attemptTrack URI if matched4Accessibility search automationBest-effort selection5Open Spotify search screenUser selects manuallyThe local catalogue is no longer the limit of what LocaLL can play. It acts as an offline seed for common tracks.The API handles requests outside that catalogue. Accessibility automation remains a fallback when API resolution isn't available, and opening the search screen is the final fallback.Regardless of which path produces the URI, playback goes through the same playUri() implementation.That separation is important: track resolution has multiple possible sources, but playback has one shared path.

6. Keeping a 1B model from inventing artistsThe local model can extract structured information such as title and artist from a spoken request.However, a small model can confidently attach an artist that was never mentioned. Passing that guess directly into a search query can produce completely unrelated results.I added three safeguards in MusicCommandHandler.kt.Catalogue fast pathKnown songs are matched locally and played without loading the model. This avoids unnecessary inference for requests that can already be resolved.Search using the raw transcriptThe first API search uses the original spoken request, not the model-generated title and artist fields.This is important because the raw transcript represents what the user actually said. The model shouldn't get an opportunity to change the request before the first search.Validate extracted artistsThe artistWasSpoken() check verifies that an extracted artist actually appears in the transcript. If it doesn't, the artist is discarded.The model is now a fallback for splitting the request into title and artist when the initial raw search doesn't resolve it. It is no longer the first or only interpretation of the user's request.

7. Remembering the last trackThere was another problem with relying entirely on media-button events.Commands such as "play it again" don't contain a track URI. Sending MEDIA_PREVIOUS isn't necessarily the same as replaying the last requested track, and the active media session might no longer be available.For short-term context, I added a deterministic MusicSession that remembers the last track's exact URI for five minutes.This allows follow-up commands such as:"Play it again.""Play that song.""Play something else."The app can resolve references to the previous track without asking the model to infer the song again.Search-first resolution also made it possible to introduce a longer-term listening history.

8. Building a local listening historyEvery successfully resolved track provides a title, artist, and Spotify URI.LocaLL stores this information in an on-device Room database. There is no listening-history backend; the history stays on the device.Once tracks are stored locally, frequency and recency become simple database queries rather than language-model problems.This enables commands such as:"Play my most played" — retrieves the most-requested track."Play my favourite artist" — retrieves the artist with the highest total request count."Play what I was listening to" — retrieves the most recent play.Each result resolves to a stored URI and goes through the same playback path.A fixed catalogue could never answer questions about what the user listened to yesterday. A local history built through actual usage can.ResultThe final implementation separates track resolution, playback, and listening history.ComponentResponsibilityNetworkLocal catalogueResolve known tracks offlineNoneSpotify Web API /v1/searchResolve requests to track URIsRead-onlySpotify deep linksOpen tracks by URINoneMedia-button eventsControl playbackNoneAccessibility serviceFallback search and selectionNoneLocal LLMExtract title and artist when neededNoneMusicSessionFive-minute follow-up contextNoneRoom listening historyStore plays and support personal queriesNoneWhat the final architecture achieves:No user login or user-consent flow.No API calls to start or control playback.One read-only search integration for resolving unknown tracks.Playback remains device-level and best-effort.API credentials are optional, with fallback to the original API-free implementation.Listening history stays on-device.What changedThe original goal was to avoid Spotify integration completely. That removed network dependencies, but it also meant relying on an external UI for something as basic as finding the right song.The final design uses the API only where it provides real value: resolving a spoken request to an exact track identity.Everything else remains on the device.The broader lesson is that avoiding an API isn't automatically the simplest or most reliable architecture. Sometimes a small, read-only integration can remove a much larger dependency on UI automation.For LocaLL, the right boundary turned out to be simple: use the API to identify the music, but keep playback and personal listening history under local control.

The final boundary

The API is used only to identify the music. Playback remains device-level and best-effort; personal listening history stays on-device. A small, read-only integration removed a larger dependency on UI automation without moving playback or personal data to a backend.

Takeaway

Avoiding an API is not automatically the simplest or most reliable architecture. Use the API to identify the music, but keep playback and personal listening history under local control.
