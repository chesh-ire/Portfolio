Running a 1B Model on Android CPU: Managing Performance and Thermal Throttling

Running a 1B model locally is straightforward with llama.cpp. Keeping inference responsive as the phone heats up is the harder problem.

The setup

LocaLL runs Llama 3.2 1B Q4_K_M entirely on the CPU. The GGUF model is bundled with the APK, so inference works offline without relying on a server or GPU. The goal was to manage CPU usage and thermal throttling during sustained use, not just get the model to run.

Understanding the CPU topology

Android devices use heterogeneous CPU cores with different performance characteristics. I added CPU topology detection in the native topology.cpp layer. It reads each core’s maximum frequency from cpufreq and classifies cores relative to the fastest core on the device.

const double perf_threshold = top_freq * 0.65;

On my test device, two cores reached 4.47 GHz and six cores reached 3.53 GHz. The six-core cluster runs at roughly 79% of the fastest cluster’s maximum frequency. A 95% threshold would exclude it, even though these cores can handle inference. A 65% threshold includes both performance clusters while excluding the lower-power tier. This is a device-specific heuristic, not a universal Android CPU threshold.

Keeping inference on a dedicated thread

InferenceDispatcher.kt uses a dedicated single-thread executor to route native inference calls. CPU affinity applies to the calling thread, so allowing requests to move between arbitrary coroutine-pool threads makes it harder to control which thread receives affinity settings. The executor provides a consistent host thread and serializes requests. This does not make inference single-threaded: llama.cpp manages its own worker threads, which perform parallel computation. The Kotlin executor only controls how requests enter the native layer. Affinity should not be assumed to pin every llama.cpp worker unless it is explicitly applied to those workers or worker creation has been verified.

Tuning decode and prefill separately

Decode generates tokens one at a time and is largely memory-bandwidth-bound. Increasing thread count beyond a point provides little benefit. Prefill processes the input prompt and is more compute-intensive, so it benefits from the wider performance cluster. In testing, decode stopped scaling meaningfully beyond four threads. More threads increased CPU activity without proportional improvement, so decode is capped at four threads while prefill can use the available performance cluster. Speech-to-text completes before LLM intent processing starts, so the workloads do not compete for CPU resources at the same time.

Benchmarking thread configurations

I added a benchmark harness to compare thread counts and CPU core configurations. Each configuration was tested seven times using a randomized, interleaved schedule with a fixed seed. This reduces bias from temperature changes during longer benchmark runs. Most differences were within the thermal noise floor, so I avoided treating small differences as meaningful. One result was clear: eight decode threads moved the device thermal state from MODERATE to SEVERE. Once the OS reduced CPU frequencies, decode performance dropped to around 0.5 tokens per second. Adding more threads had made performance worse.

Adding a thermal governor

ThermalGovernor.kt reads Android thermal status and adjusts decode thread count. As thermal pressure increases, decode parallelism is reduced:

Thermal statusDecode threads
NONE4
LIGHT3
MODERATE2
SEVERE and above1

Only decode thread count is reduced. Prefill continues to use the performance cluster. This does not prevent heating, but avoids continuing with a thread configuration that is already causing severe throttling.

Testing KV cache quantization

I tested Q8_0 quantization for the KV cache. Decode performance improved by around 16%, while prefill performance dropped by around 19%. The quantized cache reduces memory-bandwidth requirements but adds dequantization work. Since requests also include prompt processing, overall latency increased for prefill-heavy inputs. I reverted to the default F16 KV cache.

Compiler optimizations

Compiler flags had a larger impact than most thread-count changes. I enabled ARM CPU features armv8.2-a+dotprod+i8mm+fp16, improving quantized matrix operations. Depending on the operation and execution path, throughput improved around 2–4x compared with the baseline build. This compile-time optimization has a compatibility trade-off: devices without the required instruction support can fail with an illegal instruction error (SIGILL), even though the app targets arm64.

Result

  • CPU topology detection selects the faster core clusters.
  • A dedicated executor serializes native inference requests and gives them a consistent entry thread.
  • Decode is capped at four threads during normal operation.
  • Thermal status dynamically reduces decode parallelism.
  • KV cache quantization was reverted because its decode improvement did not compensate for the prefill regression.
  • ARM-specific compiler optimizations provided the largest throughput improvement.
Takeaway

A configuration that performs well in a short benchmark may not perform well during sustained use. On-device inference needs to account for CPU topology, memory bandwidth and thermal behaviour together.
