Adding Gmail Without Betraying “Local”

An app built around zero cloud inference, now with a feature that needs the mailbox. The wake word, transcription, intent detection, query generation, summary and spoken response stay on the phone. Only mailbox access touches the network.

The design boundary

“Hey LocaLL, summarise my unread email.” The wake word, transcription, intent detection, query generation, summary and spoken response should all stay on the phone. Only the part that actually needs mailbox access should touch the network. That boundary is the whole design challenge.

The structure every feature follows

There's no CommandHandler base class. Each feature follows the same convention, which makes adding another capability fairly mechanical.

Email (feature 4) follows the same structure as Music (feature 3), which follows Memory (feature 2). Each feature lives under its own voice/<feature>/ package and has four main parts:

  • Intent matching: Intents.matches() uses a deterministic keyword gate to route an utterance to the right module. Feature-specific matching happens before generic rules so that common verbs don't get intercepted by the wrong handler.
  • Command action: a CommandAction.X data class carries the raw transcript. The module owns the rest of the parsing.
  • Handler: constructed with just a Context. It is dispatched before the accessibility-service check because email commands don't need accessibility.
  • Parser: wraps the local LLM with a GBNF grammar and a few-shot prompt.

Inside the handler, the same two-tier approach applies: a fast deterministic grammar handles the common cases without invoking the model. Only genuinely free-form requests fall through to the LLM.

That keeps model inference, and its competition for the performance cores, out of the path when it isn't needed.

Where the model earns its keep

“Archive everything from last week.”

“Delete emails older than a month.”

A keyword grammar can recognise an action, but it can't reliably turn those requests into a Gmail search query. That's where the local model helps: it generates the Gmail search string, entirely offline.

EmailIntentParser.kt uses a GBNF-constrained prompt to produce structured output:

{
  "action": "delete",
  "query": "older_than:30d"
}

The grammar guarantees the JSON shape. The few-shot prompt teaches the model the intended semantics, including Gmail's search syntax. That's the part of the email workflow where the LLM earns its keep: translating a natural-language request into a mailbox query.

Summarisation is local too. The summariser reuses the same model, this time with an empty grammar so it can generate free text. Its prompt asks for two to four sentences in plain, spoken English.

It receives only header metadata: sender, subject, and snippet. Full message bodies are not sent to the summariser. A body is fetched only when a command explicitly asks to read a particular email aloud.

Drawing the network boundary

The flow is deliberately narrow:

On-device: intent detection → query generation → Gmail request → local summarisation → Piper TTS.

The Gmail request is the only part that needs the network. Everything involving AI stays on-device.

I kept the integration lightweight. Gmail is called using raw HttpURLConnection and org.json, rather than introducing a full HTTP or JSON SDK.

The only new dependency is play-services-auth, used to obtain OAuth tokens through the current Identity Authorization API.

The first consent flow has to be launched from an Activity. Once access has been granted, the always-on voice service can retrieve tokens silently. Tokens are cached for roughly 50 minutes against their one-hour lifetime.

The important distinction is that authentication and mailbox access are network operations, but they don't move the AI processing off the device.

Making “delete” safe to say out loud

Voice commands, destructive operations, and a 1B model are a combination that needs more than a good prompt. The safeguards are layered, and they fail closed.

  • Scope is mandatory. Archive and delete requests without a search query return Unknown. A vague request must never turn into an operation on the entire mailbox.
  • Confirm using the actual count. Before a state-changing operation, the app counts the matching messages and asks for confirmation: “Move 23 emails to Trash?” It never silently performs a mass action. Silence is not consent.
  • Delete means Trash. The OAuth scope is gmail.modify. It allows messages to be moved to Trash, where they remain recoverable for 30 days, but does not grant permanent-delete access. The safer interpretation of a spoken command wins.
  • Operations are bounded. Even requests such as “clear everything” have a maximum operation limit. If the result is truncated, the app logs that fact rather than silently pretending it processed everything.

The principle is simple: a model-generated query should never be enough, by itself, to authorise a destructive action.

The problem the original design didn't foresee: the mailbox isn't always reachable

The first version treated Gmail as something the app had to reach over the network for every command. That works until you ask “How many unread emails do I have?” on the subway.

It also meant fetching the same message headers repeatedly, even when the app had already seen them.

The fix was a read-through cache: EmailRepository backed by a small Room database.

The privacy boundary didn't change. The cache stores headers and, lazily, the body of a message explicitly opened by the user. It simply avoids fetching the same data again.

The repository follows three paths:

metadata(id) → cache hit? serve it : fetch, cache, serve
body(id) → fetch once, cache it → null until the first read
listMessages(query) → fetch from Gmail → on IOException, serve cached
Slice(scope)

The tricky part was deciding what to serve when a live Gmail query fails. An arbitrary Gmail search query can't simply be replayed against a local Room table.

Instead, each command declares a CacheScope: RECENT_INBOX, UNREAD_INBOX, or IMPORTANT_UNREAD. These are predefined slices that the local database can answer without needing to reproduce Gmail's search engine.

So “Summarise my unread” can degrade to the unread messages known at the last sync. But the app says so explicitly:

“You're offline, so this is from your last sync.”

Degraded results are useful. Silently presenting stale results as current is not.

Keeping the cache honest: sync in, write-through out

A cache that only fills on reads becomes stale as soon as something changes, whether that change happens on the server or inside the app. Two mechanisms keep it up to date.

Incremental sync: changes from Gmail. refresh() uses Gmail's users.history.list endpoint with the last stored historyId. Instead of downloading the mailbox again, it retrieves changes since that checkpoint: messages added or deleted, labels moved, and other mailbox updates.

Refresh runs on a best-effort basis before commands. It is wrapped so that a sync failure doesn't make an otherwise usable command fail.

The first run is deliberately different. It records a baseline historyId and returns. The cache starts empty and read-through populates it as needed.

Write-through: changes made by LocaLL. When the app archives or trashes a message, Gmail is the source of truth. But the local cache also needs to reflect the successful operation immediately.

Otherwise, the next “Summarise my inbox” could still include a message that was just archived.

So successful mutations are mirrored locally:

  • onArchived removes the INBOX label.
  • onTrashed removes the message row.

The cache reflects the user's action immediately, rather than waiting for the next sync.

The sync edge case: the checkpoint expires

Gmail only retains history for a bounded period. If the app stays unused for long enough, its stored historyId can point to a record Gmail has already removed. The API responds with a 404.

Replaying an incomplete delta on top of old cached data would be dangerous. The cache could quietly drift away from the actual mailbox.

GmailApi.history represents this explicitly as HistoryPage(tooOld = true) rather than treating it as an empty page.

The repository then does the safe thing: clear the cached state, establish a new baseline, and let read-through populate it again. 

refresh():
  no previous state → record baseline and return
  page.tooOld → clearAll() → establish a new baseline
  otherwise → apply history events
           → prune old metadata
           → advance checkpoint

Correct-but-empty is better than fast-but-lying.

Cache size is bounded too. pruneMetadataOlderThan removes metadata-only rows older than seven days, but preserves rows whose message bodies have been fetched. Those are messages the user has actually chosen to read.

Reading one email aloud without reading the junk aloud

“Read my newest email.”

“Find the email about the offsite.”

Both eventually lead to the same operation: fetching a message body and sending its text to TTS.

Raw Gmail bodies are not particularly friendly to a spoken interface. They can contain quoted reply chains, Outlook headers, quote lines, signatures, “Sent from my iPhone”, and, for HTML-only messages, a wall of markup.

Before anything reaches Piper, plainText cleans the content:

  • Walk the MIME tree, preferring text/plain.
  • If necessary, fall back to HTML and strip <style>, <script>, and other tags.
  • Decode HTML entities.
  • Stop at the first recognised reply-history or signature marker. For example, a reply header such as On ... wrote: or the standard -- signature separator can mark where the original message ends and the quoted conversation or signature begins.

These markers are heuristic, not a universal email-signature parser. Different clients format replies and signatures differently, so the goal is to remove common clutter without claiming every message can be perfectly segmented.

The result is the message itself, not the entire conversation history that came with it.

There's another problem with “Find the email about X”: there may be several matching messages. pickBest ranks the top candidates by how many topic words appear in the subject and snippet, using recency as the tie-breaker.

It then reads the best match while acknowledging the ambiguity: “I found 4 possible matches; this looks like the one.”

The app makes a best-effort selection without pretending that a fuzzy topic match is certain.

Two failures that must not look the same

A network failure and an authentication failure can look similar at the socket level, but they need very different responses.

If the network is unavailable, the app can use its cached data.

If the OAuth token has expired or access has been revoked, serving cached data as if Gmail were still connected would hide the real problem.

GmailApi throws a distinct Unauthorized error for a 401 response. Every cache-fallback path rethrows this before reaching the generic IOException handler.

That means:

  • Network failure: serve the relevant cached slice and explain that it is from the last sync.
  • Authentication failure: stop the fallback, invalidate the cached OAuth token, and ask the user to reconnect.
“Gmail access expired — reconnect in LocaLL and try again.”

The same principle from the destructive-operation guardrails applies here: the app should never hide a failure just to make a command appear successful.

What changed, and what did not

The feature now has an offline fallback, incremental sync, local mutation tracking and explicit handling for expired history checkpoints and revoked access. None of that moved AI off the phone.

  • Zero AI tokens leave the device.
  • gmail.modify allows Trash rather than permanent deletion.
  • Headers go to the summariser, while full bodies are fetched only when explicitly read.
  • Email bodies and metadata are cached locally.
  • The only new dependency is play-services-auth, for token acquisition.
Takeaway

The hard part was never just connecting Gmail. It was deciding exactly what the app needs from the network, what it can keep locally, and what it must never pretend to know.
