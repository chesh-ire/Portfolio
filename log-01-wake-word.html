Wake Word Detection Working on Android

The wake-word detector continuously listens for “Hey LocaLL”. Getting the three-stage openWakeWord pipeline running on Android meant solving dynamic tensor allocation in TFLite and a native ONNX Runtime dependency conflict.

The pipeline

Incoming 16 kHz audio passes through three sequential models:

16 kHz audio
→
Mel spectrogram
→
96-D embedding
→
Wake-word score

The first two models are shared openWakeWord models. Only the final wake-word model is custom-trained using my own voice.

1. TFLite allocation failure with dynamic input shapes

The initial plan was to convert all three models to TensorFlow Lite and run inference directly on Android. The custom wake-word model converted and loaded successfully, but the mel-spectrogram model failed during interpreter allocation. The model uses a Short-Time Fourier Transform (STFT), whose input dimensions are dynamic because incoming audio length is not fixed at conversion time. During conversion, STFT is represented using CONV_2D; the resulting dynamic dimensions caused TFLite to fail while calculating tensor allocation size.

java.lang.IllegalStateException:
Internal error: Failed to allocate memory for the melspectrogram model:
BytesRequired number of elements overflowed

I tested TFLite 2.16.1 and 2.17.0, including different resizeInput() configurations with strict mode enabled. Resizing did not resolve the unbounded dimensions in the STFT operation. I moved the pipeline to ONNX Runtime, which handled dynamic input shapes correctly. The wake-word model accepts the expected [1, 16, 96] shape, avoiding additional axis transposition.

2. ONNX Runtime dependency conflict

LocaLL already uses sherpa-onnx for on-device Piper text-to-speech. Sherpa-onnx bundles its own libonnxruntime.so. Integrating Microsoft’s ONNX Runtime Android Maven AAR introduced a conflict because both dependencies package a native library with the same name. Sherpa bundles ONNX Runtime 1.28.2, while Microsoft’s AAR provides 1.28.0. The JNI bridge expects symbols from its corresponding runtime version.

java.lang.UnsatisfiedLinkError:
cannot locate symbol "OrtGetApiBase@VERS_1.28.2"
referenced by libonnxruntime4j_jni.so

Excluding one native library would not solve the issue: the JNI bridge and ONNX Runtime core need compatible versioned native symbols.

Resolution: reuse the runtime already bundled by sherpa-onnx

Rather than adding another ONNX Runtime dependency, I reused the version already bundled by sherpa-onnx. I aligned the Java bindings and JNI library with sherpa’s existing runtime version (1.28.2), using onnxruntime-1.28.2.jar and the corresponding libonnxruntime4j_jni.so from the community Android build. Both TTS and wake-word detection now use the same libonnxruntime.so. ONNX Runtime is effectively a shared native dependency in the APK; every feature using it must agree on the runtime version and matching JNI bindings.

3. Running the detector continuously

Wake-word detection needs to run continuously, so inference overhead matters. I configured ONNX Runtime with one inference thread (intraOpNumThreads = 1) and ran the detector on a background thread with reduced priority so it would not compete unnecessarily with foreground work. The detector processes audio continuously and evaluates the confidence score against a threshold.

Result

The main challenges were not training the wake-word model. They were running preprocessing with dynamic input shapes and integrating another ONNX-based feature without native-library conflicts. Moving to ONNX Runtime solved the first problem; reusing sherpa-onnx’s runtime and matching its JNI bindings solved the second. Both wake-word detection and text-to-speech now share one ONNX Runtime installation, while the detector continuously processes audio with low measured CPU usage.

Takeaway

On Android, on-device ML integration involves more than getting a model to run. Runtime compatibility, native library packaging, thread configuration and resource usage all matter when multiple ML features coexist.
